# A-5.4C Public Listing Eligibility Read — Boundary Audit

## Décision auditée

La question est exclusivement : « ce Listing peut-il être ajouté à une
collection privée Favorites à l'instant explicitement observé ? »

L'autorité unique est `ListingLifecycle`. `Favorites` consomme la décision sans
interpréter le lifecycle, un Aggregate, une projection ou un état technique.

## Frontières existantes

- `ListingContactabilityReaderV1` décide la réception d'une intention de
  contact ; sa finalité est différente ;
- `ListingReservationAvailabilityReaderV1` décide la réservabilité ;
- `ListingModerationReaderV1` décide l'éligibilité à la modération ;
- `PublicListingQuery` sert une projection de rendu ;
- Search décide la découvrabilité ;
- Runtime Health décrit une disponibilité technique.

Aucune de ces frontières ne porte explicitement l'éligibilité Favorites. Une
frontière publique owner-scoped additive sera donc nécessaire, sous un futur
Contracts Amendment distinct.

## Décision publique minimale candidate

Entrées documentaires minimales :

- identité canonique `ListingId` existante ;
- instant d'observation explicite, immutable, UTC et canonique.

Catalogue public fermé candidat :

- `Eligible` ;
- `NotEligible` ;
- `Missing` ;
- `Corrupted` ;
- `DependencyUnavailable`.

Seul `Eligible` autorise l'ajout. Les statuts lifecycle, motifs, dates internes,
versions, snapshots, contenus et diagnostics restent internes.

## Conclusion

Une frontière publique owner-scoped `ListingLifecycle` est faisable et
nécessaire. Le présent audit ne la crée pas et n'ouvre aucune Foundation.
