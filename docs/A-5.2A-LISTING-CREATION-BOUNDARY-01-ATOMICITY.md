# A-5.2A-LISTING-CREATION-BOUNDARY-01 — Atomicity & Concurrency

## Journal d'intents futur

Owner : ListingLifecycle. Clé unique : `(operation, intent_id)`. Colonnes
conceptuelles : operation, intentId, checksum, listingId, propertyId, result,
createdAt. Aucun FK cross-domain et aucune PII.

## Algorithme normatif

1. ouvrir/rejoindre la transaction locale Listing ;
2. réserver l'intent par unicité ;
3. si existant, comparer le checksum canonique ;
4. retourner `AlreadyApplied` ou `DivergentIntent` sans mutation ;
5. vérifier Property via le port public ;
6. exécuter la création avec l'Aggregate et le mapper certifiés ;
7. persister racine, première révision et résultat d'intent ;
8. commit unique ; toute erreur provoque rollback intégral.

## Courses

| Course | Résultat convergent |
|---|---|
| même intent, même payload | un `Applied`, autres `AlreadyApplied` |
| même intent, payload différent | un `Applied`, autres `DivergentIntent` |
| intents différents, même ListingId | un `Applied`, autres `ListingIdConflict` |
| échec après réservation | rollback intent + Listing |
| retry après déconnexion au commit | relecture intent, résultat déterministe |

## Future migration

Une migration additive postérieure à 054 pourra créer uniquement le journal
owner-scoped. Les migrations et tables existantes ne seront pas modifiées.

## Transaction existante

Les garanties commit/rollback de `PostgreSqlListingTransaction` sont
préservées. La future composition devra ajouter la capacité de rejoindre une
transaction ou d'utiliser un savepoint sans modifier les résultats métier.
