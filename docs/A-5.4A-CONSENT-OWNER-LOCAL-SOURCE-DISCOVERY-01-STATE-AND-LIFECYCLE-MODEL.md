# A-5.4A-CONSENT-OWNER-LOCAL-SOURCE-DISCOVERY-01 — State and Lifecycle Model

## États conceptuels

| État | Sens | Résultat Reader |
|---|---|---|
| `Undecided` | intention connue, aucune décision positive | `Denied` |
| `Granted` | consentement applicable à l'instant | `Granted` |
| `Denied` | refus explicite | `Denied` |
| `Withdrawn` | accord antérieur retiré | `Denied` |
| `Expired` | accord hors période, uniquement si une politique future le prévoit | `Denied` |

`Missing`, `Corrupted` et `DependencyUnavailable` sont des résultats de
lecture, pas des états métier persistés.

## Création de l'intention

L'enregistrement initial peut matérialiser `Undecided`. L'absence complète
d'une intention retourne `Missing`. Cette distinction évite d'interpréter une
absence technique comme un refus explicitement enregistré.

## Transitions conceptuelles

- création → `Undecided` ;
- `Undecided` → `Granted` ou `Denied` ;
- `Granted` → `Withdrawn` ;
- `Granted` → `Expired` seulement si une règle d'expiration est ultérieurement
  certifiée ;
- une nouvelle décision après retrait exige une nouvelle révision explicite ;
- aucune révision existante n'est modifiée ou supprimée silencieusement.

Le modèle ne prescrit pas de Command, d'Entity ou de lifecycle exécutable.

## Temporalité

Chaque révision distingue :

- l'instant d'effet métier ;
- l'instant d'enregistrement technique.

La lecture à `LeadConsentObservedAt` sélectionne la dernière révision applicable
par instant d'effet, puis par révision monotone. Les égalités ou chronologies
ambiguës produisent `Corrupted`.

Une décision enregistrée ultérieurement ne réécrit pas le résultat historique
d'une observation antérieure.

## Versionnement

Une version monotone par `LeadIngressIntentId` est requise pour :

- ordonner les révisions concurrentes ;
- détecter les trous et duplications ;
- appliquer l'optimistic locking ;
- garantir un replay déterministe.

Le journal append-only est l'autorité. Un état courant éventuel est une
optimisation dérivée et ne peut pas remplacer l'historique.

## Idempotence et concurrence

- même intent, même révision et même checksum : replay identique ;
- même intent/révision, checksum différent : divergence fail-closed ;
- prochaine révision différente de `current + 1` : conflit ou corruption ;
- deux écritures concurrentes : une seule révision peut être appliquée ;
- toute écriture et son journal d'idempotence futur partagent une transaction
  owner-locale ;
- rollback : aucune révision partielle visible.
