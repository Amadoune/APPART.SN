# A-5.3-BASELINE-IMPORT-WHITESPACE-QUALIFICATION-01

## Statut

GO CERTIFIÉ — FERMÉ.

## Objet

Qualifier les 239 erreurs `new blank line at EOF` révélées par
`git diff --cached --check` pendant la première matérialisation Git de la
baseline certifiée.

## 1. Qualification technique

### Nature exacte

`blank-at-eof` est une règle de whitespace de Git. Lorsqu'un fichier ajouté se
termine par plusieurs séquences de fin de ligne, Git considère les lignes
vides situées après la dernière ligne utile comme des erreurs.

Les 239 fichiers concernés présentent exactement :

```text
dernière ligne utile
LF
LF
```

La normalisation strictement bornée consiste à obtenir :

```text
dernière ligne utile
LF
```

Elle retire donc exactement un octet `0A` par fichier.

### Distinctions

| Écart | Définition | Présent ici |
|---|---|---|
| `new blank line at EOF` | ligne vide ajoutée après la fin utile | oui |
| `missing newline at EOF` | absence du LF terminant la dernière ligne | non |
| trailing whitespace | espaces ou tabulations après un contenu | non |
| indentation | espaces en début de ligne utile | non |
| modification de contenu | changement d'un caractère utile | non |

### Impacts

- Git : le blob et son SHA-256 changent nécessairement d'un octet ;
- SQL : aucun token, séparateur, commentaire, littéral ou ordre SQL ne change ;
- Markdown : aucun titre, tableau, bloc ou paragraphe ne change ;
- rendu Markdown : identique ;
- PostgreSQL : le whitespace terminal est ignoré après le dernier `;` ;
- checksums fonctionnels : aucun checksum métier ne dépend des octets des
  migrations ou documents concernés ;
- manifeste de baseline : doit être régénéré après normalisation.

L'analyse du runner confirme qu'il lit puis exécute le SQL. Aucun registre de
checksum des fichiers de migration n'est utilisé comme autorité applicative.

### Identité SQL

Après la normalisation proposée, le SQL est :

- lexicalement identique pour tous les tokens SQL ;
- syntaxiquement identique ;
- sémantiquement identique ;
- différent uniquement au niveau de la représentation binaire et du hash du
  fichier.

Le qualificatif « strictement identique » est donc recevable aux niveaux
lexical SQL, syntaxique et sémantique, mais pas au niveau octet ni SHA-256.

## 4. Qualification des preuves

| Option | Qualification |
|---|---|
| 1 — aucun rejeu | insuffisant pour des migrations gelées |
| 2 — Git uniquement | suffisant pour Markdown, insuffisant pour SQL gelé |
| 3 — Architecture + PHPStan + Pint | PHPStan/Pint n'exécutent pas les migrations |
| 4 — Architecture + PostgreSQL | proportionné et complet |
| 5 — campagne complète | recevable mais non nécessaire à un retrait de LF |

### Preuves retenues

L'option 4 est normative :

- `git diff --cached --check` ;
- vérification que seuls les 239 fichiers autorisés changent ;
- preuve d'un seul octet `0A` retiré par fichier ;
- Architecture complète ;
- PostgreSQL complet, incluant migrations et rollbacks ;
- régénération et contrôle du manifeste SHA-256 ;
- `git diff --check` terminal.

PHPStan, Pint et la suite applicative complète ne sont pas nécessaires puisque
ni PHP ni logique applicative ne changent. Ils peuvent être rejoués sans devenir
une condition spécifique de cet amendement.

## 5. Options de gouvernance

### Option A — normalisation bornée

- restaure la gate Git sans exception ;
- produit une baseline reproductible ;
- ne modifie aucun token SQL ni contenu Markdown ;
- nécessite l'autorisation explicite de toucher les migrations gelées ;
- permet de vérifier chaque changement par une règle mécanique unique.

### Option B — exception Git documentée

- conserve les octets historiques ;
- laisse `git diff --cached --check` en échec ;
- affaiblit une gate normative et crée une exception durable ;
- rend les futures importations moins reproductibles.

### Option C — report définitif

- préserve les fichiers ;
- empêche toute matérialisation et tout freeze ;
- ne résout aucune dette opérationnelle.

## Recommandation unique

Retenir l'option A.

Autoriser un amendement d'implémentation limité exactement aux 239 chemins déjà
signalés. La transformation autorisée doit supprimer uniquement le second LF
terminal. Toute autre différence doit entraîner un arrêt immédiat et un NO GO.

Cette normalisation est textuelle et non fonctionnelle. Elle reste néanmoins
une modification binaire des migrations gelées et ne peut être appliquée sans
un nouveau prononcé explicite.

## Hors périmètre

- toute autre correction de whitespace ;
- modification de code, test, contrat ou configuration ;
- changement de commentaire ou de contenu documentaire ;
- changement de token SQL ;
- ajout d'une exception Git ou affaiblissement de `core.whitespace` ;
- commit, tag ou fermeture de 5.3L.
