# A-5.4B Reservation Availability Source — Idempotence and Concurrency Matrix

| Cas | Résultat conceptuel |
|---|---|
| même intent, révision et checksum | replay identique, aucune seconde écriture |
| même intent/révision, checksum différent | divergence fail-closed |
| révision suivante continue | append autorisable |
| saut ou recul de révision | rejet de continuité |
| deux acquisitions chevauchantes | une seule peut gagner la sérialisation owner-locale |
| erreur avant append | rollback total |
| erreur après savepoint interne | retour au savepoint sans commit partiel |

La future sérialisation devra être durable et limitée au sujet/fenêtre. Une
contrainte PostgreSQL ou un verrou transactionnel ne pourra être choisi qu'en
Persistence Foundation, preuves de concurrence à l'appui.

Une lecture `Available` reste informative : seule une future opération
atomique d'acquisition pourra garantir l'absence de double réservation.
