# A-5.2A-LISTING-CREATION-BOUNDARY-01 — Boundary Audit

## 1. Constat

`CreateDraft` est une classe Application concrète. Elle :

- dépend directement de `ListingRegistry`, `PropertyCatalog` et de la policy ;
- construit puis retourne l'Aggregate `Listing` ;
- appelle `ListingRegistry::add()` ;
- ne possède ni Command V1, ni Result fermé, ni intentId ;
- n'est pas un port public destiné à un domaine consommateur.

`ListingRegistry` est un port de persistence, pas une API métier publique.

## 2. Persistence existante

`PostgreSqlListingRepository::add()` insère la racine et les révisions dans une
transaction locale. Une violation unique devient `ListingIdConflict`.
L'association PropertyId est persistée dès la création et aucun use case ne la
modifie. L'historique est append-only.

## 3. Lacune d'idempotence

Le schéma ne mémorise pas `intentId`. Une simple relecture par ListingId ne
permet pas de distinguer :

- replay identique ;
- même intent avec un ListingId différent ;
- même intent avec des données différentes ;
- collision indépendante sur ListingId.

Un journal d'intents propriétaire est donc nécessaire pour garantir
`AlreadyApplied` et `DivergentIntent`.

## 4. Atomicité requise

Le journal et la création Listing doivent partager une transaction PostgreSQL.
Écrire l'intent avant ou après `ListingRegistry::add()` créerait une fenêtre de
perte ou de double application.

La future composition doit conserver les mêmes inserts, contraintes et
rollback, sur la même connexion, avec support d'une transaction englobante ou
de savepoints. Elle ne peut pas contourner le mapper ou réécrire directement
une nouvelle représentation du Listing.

## 5. Conclusion

Compatible par extension architecturale additive. Aucun changement de règle
métier ou de lifecycle n'est nécessaire, mais l'extension exige l'autorisation
versionnée du présent amendement avant code.
