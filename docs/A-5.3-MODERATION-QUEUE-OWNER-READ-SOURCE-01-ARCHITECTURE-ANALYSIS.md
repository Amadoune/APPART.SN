# A-5.3-MODERATION-QUEUE-OWNER-READ-SOURCE-01 — Architecture Analysis

## Frontière cible

```text
future ReadModerationQueueV1
        ↓
future Queue Owner Read Source
        ↓
moderation_reports.queue_items
```

La source reste Application read-only et son adapter PostgreSQL reste en
Infrastructure. Aucun DTO de persistence ne franchit la frontière.

## Garanties

- owner unique `ModerationReports.ModerationQueue` ;
- aucune lecture cross-domain ;
- aucune dépendance à HTTP ou Laravel dans le contrat futur ;
- aucune reconstruction depuis Event ou Outbox ;
- aucune mutation, transaction métier, advisory lock ou claim ;
- résultat fail-closed sur corruption ou dépendance indisponible ;
- pagination stable sous insertions concurrentes grâce au keyset.

## Cohérence concurrente

La lecture est un instantané `READ COMMITTED`. Une modification concurrente peut
faire évoluer un item entre deux pages, mais ne doit jamais produire une
duplication due à l'offset puisque celui-ci est interdit.

Le curseur fixe la frontière de tri, pas une photographie globale. Cette
sémantique doit être explicite dans le futur contrat. Une cohérence
snapshot-isolation multi-page n'est ni nécessaire ni souhaitée.

## Éléments réutilisables

- table et mapper Queue owner-local ;
- identité stable `queue_item_id` ;
- états fermés ;
- `source_version` ;
- ordre de claim déjà indexé.

Le store de mutation existant ne doit pas être exposé à HTTP. La source de
collection devra être un port read-only séparé.
